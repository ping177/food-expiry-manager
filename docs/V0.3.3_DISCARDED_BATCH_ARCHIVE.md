# v0.3.3 规格：Discarded Batch Archive Flow

## Objective

把当前库存批次的“删除”改为逻辑删除：将 `inventory_batches.status` 从
`active` 更新为 `discarded`。`discarded` 与 `consumed` 一起进入现有“已归档”，
但卡片和详情分别显示“已删除”和“已消耗”。Archive 中的历史批次仍允许真正
hard delete；Product deletion 继续复用 v0.3.2 的 RPC 与 Storage cleanup contract。

## Tech Stack

- React 19 + Vite
- Supabase Postgres / Storage
- Vitest
- Tailwind CSS 3

## Code Style

保持现有函数式 React、Tailwind utility 和小型纯函数风格。状态文案由共享函数
统一映射，查询仍使用 Supabase builder 的 owner / status 条件：

```js
const { data: discardedBatch, error } = await supabase
  .from('inventory_batches')
  .update({ status: 'discarded' })
  .eq('id', batchId)
  .eq('user_id', session.user.id)
  .eq('status', 'active')
  .select('id')
  .maybeSingle()
```

## Testing Strategy

- 纯函数测试：Archive 状态文案、双状态筛选与 active 隔离。
- 查询合同测试：active 使用 `status='active'`；Archive 使用
  `status in ('consumed', 'discarded')` 并按 `updated_at DESC` 排序。
- 组件测试：Archive 卡片和详情区分“已消耗 / 已删除”；active 删除确认文案说明
  进入 Archive；历史删除继续保持 hard delete 入口。
- App source contract：active 只允许状态 UPDATE 且检查 0-row；Archive 才允许
  archived 状态 DELETE；Product deletion / Storage cleanup 现有回归合同继续通过。
- 完成验证：targeted tests、完整 `npm test`、`npm run build`、`git diff --check`。

## Boundaries

- Always：按当前用户和当前状态限定写入；检查 Supabase 返回行；保留 Product 与
  其他 batch；保持 Archive 搜索、分类和排序语义。
- Ask first：新增 migration、数据表、依赖、RLS / RPC / Storage contract 或生产数据操作。
- Never：active batch hard delete、删除 Product / 图片、回收站导航、恢复 discarded、
  批量删除、Category Navigation 或真实 Production Supabase 操作。

## Data Model Decision

无需 migration。现有 `inventory_batches.status` 已允许 `active`、`consumed`、
`discarded`；v0.3.2 Product deletion RPC 已覆盖 `consumed / discarded` 历史清理。

## Success Criteria

- active 删除确认后只执行 `status='discarded'` UPDATE；0-row 视为失败。
- discarded 不再出现在 active inventory，且进入 Archive。
- Archive 同时读取、筛选和排序 consumed / discarded。
- consumed 显示“已消耗”，discarded 显示“已删除”。
- Archive 中两种历史状态均可 hard delete。
- Product deletion 的 active guard、历史批次清理和 Storage cleanup contract 无回归。
- 无新增 migration、依赖、导航或恢复流程。
